## Addendum - Re-verification of the two fixes (2026-10-05)

Both initially rejected rules were re-checked from scratch after the Why edits; all other sections of each file were left untouched.

- **`swift-doc-parameter-section` - verified (flipped).** The Why now reads "the sample comment in the guidelines includes a Parameters section", which matches the guidelines text: the sample's `- Parameter separator:` / `- Parameter terminator:` bullets are annotated "Parameters section" (followed by `- Note:` / `- SeeAlso:` under "Symbol commands"). Snippets unchanged and re-typechecked 2/2 in default and Swift 6 modes; Bad/Good still demonstrate the decision; structural audit clean (id/path, frontmatter, fences, `related` + See Also links, no anti-slop).
- **`swift-doc-orphaned` - verified (flipped).** The new trigger list matches SwiftLint 0.65.1 and `OrphanedDocCommentRule.swift` exactly: a regular comment between the doc comment and the declaration (re-run: Bad -> 1 `orphaned_doc_comment` violation, Good clean), a later doc comment separated from the first, and a doc comment with no declaration after it. Blank-line-only inputs remain clean (re-run), confirming the removed claim is correctly gone. Snippets re-typechecked 2/2 in both modes; structural audit clean.
- **Non-blocking caveat (`doc-orphaned`).** The remaining sentence "Documentation tooling associates `///` comments with the syntax that follows them, so an interleaved regular comment leaves the declaration undocumented" overstates the consequence on the current baseline. Re-tested on Swift 6.4: `swift-symbolgraph-extract` still attaches the doc comment, `docc` still renders the abstract, `sourcekit-lsp` hover still shows it, and SwiftSyntax's `Trivia.docCommentValue` still returns the last doc block - for both a plain regular comment and a `swiftlint:disable` comment interleaved (the 2019 issue #2989 that motivated the rule predates the modern DocC pipeline; the doc block is only shadowed when a *later doc comment* follows). The qualitative point - keep the comment directly above the declaration, as the rule requires - holds, and the trigger claims, enforcement, snippets, and decision are all correct. Suggested future reword (not required for verification): "so the comment no longer sits directly above the declaration, which is the adjacency the rule requires."
- **Final counts: verified 24/24 (`doc` 12/12, `style` 12/12), rejected 0. Blockers: none.**
