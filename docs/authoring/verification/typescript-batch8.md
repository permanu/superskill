## `conc-shared-buffer-isolation` browser scope assessment

Acceptable. The rule is explicitly browser-scoped ("Browsers expose `SharedArrayBuffer`..."), cites MDN web-platform docs, and its Good snippet gates on `crossOriginIsolated`, a browser global that the harness types via the default DOM lib. MDN's own example gates construction the same way ("To use shared memory your document must be in a secure context and cross-origin isolated. You can use the Window.crossOriginIsolated ... properties to check"). Headless Chrome 154 on a non-isolated page: `crossOriginIsolated` false, `typeof SharedArrayBuffer` `"undefined"`, `new SharedArrayBuffer(16)` -> `ReferenceError: SharedArrayBuffer is not defined` (a throw, as the Why says). The rule does not claim to apply to Node, where `SharedArrayBuffer` is unconditionally available; that is a platform difference, not a false claim.

## `conv-string-explicit` vs verified `style-template-strings` dedup assessment

Not duplicates; both keep. `style-template-strings` is about building a string that interpolates a value (`"count: " + count` -> `` `count: ${count}` ``); `conv-string-explicit` is about converting a single value to text (`"" + value` -> `String(value)`), and MDN's `String` page explicitly states "you should not use `"" + x`". The Bad snippets and the decisions differ, and each rule links the other. Highest token-Jaccard across the pack is this pair at 0.35 (below the 0.45 near-duplicate threshold used in this pack's prior batch reports). Also reviewed: `conc-microtask-starvation` vs verified `async-microtask-defer` (continuous re-queuing -> timer vs one-off deferral -> microtask; complementary, cross-linked, no contradiction), `const-fresh-default` vs `const-default-parameter` (shared mutable default vs default-in-signature placement), `const-object-freeze` vs `const-deep-freeze` (shallow vs nested), `const-readonly-props`/`const-static-readonly` vs verified `api-readonly-fields` (interface property vs class static vs class instance field), and `conv-number-explicit` vs `conv-parseint-radix` vs `conv-number-validate` (choose conversion vs choose parse base vs validate result).

## Source evidence (claim-specific)

- `conc-yield-long-work` / `conc-no-busy-wait`: Node "Don't Block the Event Loop" - "You could partition your calculations so that each runs on the Event Loop but regularly yields (gives turns to) other pending events." Probes: a 20M-iteration synchronous loop kept a 5ms timer from firing during the loop; the chunked form with `await new Promise((r) => setTimeout(r, 0))` let it fire. Spin-wait probe: the Bad form never exited (killed at 400ms); the awaited form exited after 10ms.
- `conc-transfer-buffers`: MDN Transferable objects - "When such a buffer is transferred between threads, the associated memory resource is detached from the original buffer and attached to the buffer object created in the new thread"; "the transferable array only indicates how certain resources should be sent, but does not actually send them (although they would always be detached)". Probes: Node `MessagePort.postMessage(buffer, [buffer])` -> sender `byteLength` 0, receiver 1024; Chrome worker -> sender 0 with transfer vs 1024 without.
- `conc-shared-memory-atomics`: MDN Atomics - "Atomic operations make sure that predictable values are written and read, that operations are finished before the next operation starts and that operations are not interrupted"; `Atomics.add()` "Adds the provided value ... Returns the old value at that index". Probe: `Atomics.add(ta, 0, 1)` -> 0, `Atomics.load` -> 1.
- `conc-shared-buffer-isolation`: MDN SharedArrayBuffer - see scope assessment above; "the constructor on the global object is hidden, unless the two headers mentioned above are set"; "Unless the two headers mentioned above are set, the various postMessage() APIs will throw for SharedArrayBuffer objects".
- `conc-structured-clone-worker`: MDN Structured clone - "Property descriptors, setters, getters, and similar metadata-like features are not duplicated"; "The prototype chain is not walked or duplicated". Probes: `structuredClone(new Task("t1"))` -> own props `{"id":"t1"}`, `label` undefined, prototype `Object.prototype`; Chrome worker postMessage reproduced the same.
- `conc-worker-errors`: MDN `Worker` - "error Fires when an error occurs in the worker"; MDN `Worker/error_event` - "The error event of the Worker interface fires when an error occurs in the worker"; MDN Using Web Workers - "When a runtime error occurs in the worker, its onerror event handler is called. ... The event doesn't bubble and is cancelable; to prevent the default action from taking place, the worker can call the error event's preventDefault() method." WHATWG HTML §10.2.5 - "Whenever an uncaught runtime script error occurs in one of the worker's scripts, ... the user agent will report it for the worker's WorkerGlobalScope object." None of these terminate the worker; Chrome probe: after `throw`, 1 error event fired and the worker still answered `"alive:ping"`. See Rejects.
- `conc-worker-terminate`: MDN `Worker` - "Worker.terminate() Immediately terminates the worker. This does not let worker finish its operations; it is halted at once."; Using Web Workers - "The worker thread is killed immediately." Probe: message flow stops after `terminate()`. The "copy of the module graph" phrasing is implementation detail not spelled out on the page but inherent to the worker lifecycle (the thread and its global state persist until termination) - note, not a blocker.
- `conc-abort-composition`: MDN `AbortSignal.any` - "The returned abort signal is aborted when any of the input iterable abort signals are aborted. The abort reason will be set to the reason of the first signal that is aborted."; "Internally, the combined signal and its source signals are linked through weak references." Probes (Node and Chrome): combined aborts when one input aborts, `reason` preserved, other input untouched.
- `conc-interval-cleanup`: MDN `Window.setInterval` - "This identifier ... can be passed to clearInterval() to stop the repeated execution of the specified function"; "You can cancel the interval using clearInterval()." Probe: a bare `setInterval` keeps the Node process alive (killed by timeout), and clearing it lets the process exit. The "keeps the process alive" clause is Node runtime behavior not stated on the cited MDN page - note, not a blocker.
- `conc-listener-once`: MDN `EventTarget.addEventListener` - "once Optional A boolean value indicating that the listener should be invoked at most once after being added. If true, the listener would be automatically removed when invoked."; the page also documents that removal needs the kept function reference ("it is not possible to call removeEventListener() because no reference to the anonymous function is kept"). Probe: one dispatch pair with `{ once: true }` -> 1 call.
- `conc-microtask-starvation`: MDN Microtask guide - "If a microtask adds more microtasks to the queue by calling queueMicrotask(), those newly-added microtasks execute before the next task is run. That's because the event loop will keep calling microtasks until there are none left in the queue, even if more keep getting added."; microtasks run "before any event handlers, timeouts and intervals, or other callbacks are processed". Probe (Chrome): a zero-delay timer did not fire before a 100,000-iteration microtask chain finished.
- `const-object-freeze`: MDN `Object.freeze` - "Freezing an object prevents extensions and makes existing properties non-writable and non-configurable."; "Any attempt to do so will fail, either silently or by throwing a TypeError exception (most commonly ... in strict mode)." Probe: strict-mode assignment throws TypeError. The `as const` contrast is the type-level counterpart and is standard TS behavior.
- `const-deep-freeze`: MDN `Object.freeze` - "values that are objects can still be modified, unless they are also frozen"; "freeze is shallow". TS Handbook Objects - "Using the readonly modifier doesn't necessarily imply that a value is totally immutable". Probe: nested property mutated through a frozen parent. The Good's `declare function deepFreeze` is declaration-level and self-contained (compiles).
- `const-named-magic`: typescript-eslint `no-magic-numbers` - "Disallow magic numbers"; the page defers options to core ESLint, whose `enforceConst` is "false by default" (numbers in variable declarations are not reported by default), so the Bad `retries > 3` is flagged and the Good `const MAX_RETRIES = 3` is allowed with a default configuration.
- `const-readonly-props`: TS Handbook Objects - "a property marked as readonly can't be written to during type-checking"; "While it won't change any behavior at runtime".
- `const-static-readonly`: TS Handbook Classes - "readonly Fields may be prefixed with the readonly modifier. This prevents assignments to the field outside of the constructor."; static members are documented on the same page.
- `const-fresh-default`: MDN Default parameters - "The default argument is evaluated at call time. Unlike with Python (for example), a new object is created each time the function is called." Probe: a module-level array default accumulated `["a","b"]` across calls.
- `const-default-parameter`: same MDN page documents signature defaults; the rule is a `prefer` placement/style decision (signature over body fallback), not a behavior claim. Behavior note: a signature default also fires for an explicit `undefined`, which is the usual intent.
- `conv-number-explicit`: MDN Unary plus - "attempts to convert it into a number"; "unary plus is the fastest and preferred way of converting something into a number". MDN Number - "+x does exactly the number coercion steps ... The Number() function: Number(x) uses the same algorithm ... except that BigInts don't throw a TypeError". Probes: `+"abc"` and `Number("abc")` both NaN; `+1n` throws TypeError while `Number(1n)` returns 1. The rule is a `prefer`/review explicitness stance; MDN's "preferred" remark concerns unary plus vs unary negation, and the rule's readability rationale is the editorial half - noted, not a contradiction of fact.
- `conv-parseint-radix`: ESLint `radix` - "Enforce the use of the radix argument when using parseInt()"; "By default, parseInt() will autodetect decimal and hexadecimal (via 0x prefix). MDN `parseInt` - "If 0 or not provided, the radix will be inferred based on string's value. Be careful - this does not always default to 10!"; `0x`/`0X` prefix -> radix 16. Probes: `parseInt("0x10")` -> 16, `parseInt("0x10", 10)` -> 0, `parseInt("071")` -> 71 (modern).

- `conv-locale-compare`: MDN `String.prototype.localeCompare` - "returns a number indicating whether this string comes before, or after, or is the same as the given string in sort order. ## Rejects (left `status: draft`)

1. `typescript-conc-worker-errors` - Why/source mismatch. The Why states "An uncaught error inside a worker terminates it and surfaces as an error event on the worker object; without a listener the failure is easy to lose, and the task that posted work waits forever." In browsers, an uncaught error does not terminate a dedicated worker: MDN `Worker` and `Worker/error_event` say only that the error event fires; MDN Using Web Workers documents the event as cancelable with a preventable default action and says nothing about termination; WHATWG HTML §10.2.5 says the error is "report[ed] ... for the worker's WorkerGlobalScope object". Headless Chrome 154 probe: the worker threw on one message, fired exactly one error event, and then answered a subsequent `postMessage` (`"alive:ping"`) - it was still running. The follow-on "the task that posted work waits forever" rests on the false premise (the worker can still reply after an uncaught error). The decision itself (attach an error listener when starting a worker) is sound and the snippets compile; the fix is a Why edit, e.g. "An uncaught error inside a worker is reported as an error event on the worker object; without a listener the failure is easy to lose." If the intended scope were Node `worker_threads` (where an uncaught exception does terminate the thread and the API is `worker.on("error")`), the rule would need to be rewritten for that API instead - the current snippet is the DOM `Worker` API.
