## Notes / follow-ups (outside verifier ownership)

- `proj-inlinable` is the single rejection: the Bad example satisfies the rule's own stated criteria for a good `@inlinable` candidate, so the pair does not demonstrate the decision. It stays `draft` until re-authored (suggested fix in the table) and re-verified.
- `mem-reserve-growth` restates Apple's literal wording ("increases the array's capacity by exactly the requested amount"); the runtime trace shows the implementation pads capacity (increments of 8-16 per pass rather than exactly 10), but the qualitative claim - arithmetic vs geometric growth, reallocation count scaling with n - holds and is directly from the cited page. Not a blocker.
- `proj-package-access`: `-package-name` requirement is inherent; SwiftPM supplies it for every target. No rule edit needed. If the project validator ever compiles snippets in a stricter harness, that rule may need an exemption note.
- `proj-unavailable`: the Bad shows an internal initializer rather than a public one; the Good demonstrates the pattern and the negative probe confirms the diagnostic, but the Bad could be strengthened to a public init next to a factory to make "always wrong" concrete. Not blocking.
- `INDEX.md` header (`Rules: 121 (verified: 96)`) will be stale after these 24 flips (should read `verified: 120`); index owner's action, outside this verifier's ownership.
